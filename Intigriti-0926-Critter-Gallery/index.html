Step 01 · First contact

Eight tiles and a single parameter

The page is a grid of eight animal tiles — fox, panda, lion, penguin, otter, koala, owl, tiger. No login, no forms, no upload, nothing to report. The entire attack surface is in the href of the tiles, and it is the same attribute eight times over.

Base64 in a URL is worth a second look every single time. It is almost never there for security — it is there because a developer wanted the parameter to look opaque, or because it was the quickest way to avoid thinking about escaping. Either way it tells you the value is being decoded before it is used, and decoding is the step where assumptions get made.

Step 02 · Clearing the board

Everything obvious is already dead

Before getting clever, I spent ten minutes proving the easy answers wrong. This is worth doing properly, because every minute spent on a sink that cannot fire is a minute not spent on the one that can.

The heading is escaped

Decoded picRendered
<b>xx</b>&lt;b&gt;xx&lt;/b&gt;
"><img src=x onerror=alert(1)>&quot;&gt;&lt;img src=x …
fox<script>alert(1)</script>fox&lt;script&gt;…

Every angle bracket comes back as an entity. That is htmlspecialchars() doing its job, and no amount of encoding tricks moves it — the base64 layer is decoded before the escaping runs, so there is no second parser to desynchronise.

There is no file behind it

Base64 of ../../etc/passwd echoes the path in the heading and produces no description. Same for ./fox, fox.txt, fox/../fox. Nothing resolves, so nothing is being opened. Feeding it bytes that are not valid base64 decodes to binary garbage which is echoed as-is — which tells us the decode is plain, non-strict base64_decode() with no validation performed on the result.

Dead end

At this point the honest read is that the page has one escaped sink and one lookup that returns a fixed string from a fixed set. That is not a vulnerability. The mistake would be to stop here — the description lookup had not actually been tested, only used.

Step 03 · The tell

One uppercase letter

I asked for FOX instead of fox — ?pic=Rk9Y — for no better reason than working through case variants. The response contradicts itself.

Put it side by side with Shot 0. Same critter, same panel, one letter of difference in the request — and the fox face has been replaced by an empty frame while the sentence next to it has not changed by a single character. Nothing built on one hardcoded array can produce that. Two separate things went looking for FOX, and only one of them found it.

The whole finding

A case-sensitive lookup in PHP is an array key. A case-insensitive one, performed on a string that came from the user, is a database comparison under a _ci collation. The picture is hardcoded. The description is being queried.

Step 04 · Break it

A single quote takes the page down

If there is a query, a stray quote should break it. Base64 of fox' is Zm94Jw==.

This is more informative than an error message would have been. PHP died partway through building the page and returned what it had, which was nothing. A quote in a value that is only ever printed cannot do that. A quote in a value that is concatenated into a query does exactly that.

Worth noting for anyone reproducing: the response is still 200. If you were grepping for a non-200 status to find the injection you would have walked straight past it.

Step 05 · Repair it

A comment puts it back together

If a quote broke the statement, a comment should fix it by swallowing whatever the application appends after my input. Base64 of fox'-- is Zm94Jy0tIA==.

Mind the space

MySQL requires whitespace after the -- comment marker. The trailing space in fox'-- is load-bearing. It survives base64 intact, but it is the single easiest thing to lose when editing payloads by hand — and losing it turns a working injection into a silent failure that looks exactly like Shot 2, which looks exactly like "there is no bug here".

Break, then repair. Two requests, and the shape of the statement is no longer a guess.

Step 07 · Shape

One column, and it renders

To use UNION I need the column count of the original SELECT. ORDER BY 1 works and ORDER BY 2 breaks, which says one column. Confirming it with a union — base64 of zz' UNION SELECT 1-- — also answers a second question: does my value actually reach the page?

From here the vulnerability is no longer "can I break the query". It is "what would I like the database to tell me". Everything after this is bookkeeping.

Step 08 · Fingerprint

Which engine am I talking to

Different engines expose their metadata in incompatible ways, so before enumerating anything I need to know which one this is. sqlite_version() errors; @@version answers.

MySQL means information_schema is available, which means the database will describe its own structure to me on request. It also retroactively explains Step 03: MySQL's default collations are case-insensitive, which is exactly why FOX matched fox while the PHP array did not.

Step 09 · The schema

A table the gallery never mentions

Now I ask the database what tables it holds in the current schema.

I used group_concat() deliberately. The page renders one column but happily prints a long string, so collapsing an entire result set into a single comma-separated value turns what would have been a row-by-row extraction into one request.

Next, the columns — I need a field name before I can select anything out of that second table.

This is the part worth pausing on outside of a challenge context. secret_vault was never meant to be reachable from the web tier at all — and the injection does not care, because the database user holding the connection was granted SELECT across the whole schema.
