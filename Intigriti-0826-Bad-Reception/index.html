Step 02 · The fault

Why the picture breaks the moment you tune

On page load the TV plays fine, because that <source> child is an absolute path. The moment you press a channel key the picture dies. The reason is pure URL resolution:

setTube() sets src on the <video> element, which overrides the child <source>, and the value is relative to /challenge, so it lands at the web root and 404s.

Trap

This is the challenge's title and its most visible defect, so it pulls hard as "the bug". It isn't. Repairing the picture is achievable and yields nothing. I lost time here before accepting that the broken TV is scenery: a puzzle that teaches you the URL layout you'll need at the very end.

Finding 1

The server checks only that channelId[0] is a decimal digit. Everything after that first character is unvalidated. A single leading 1 buys arbitrary HTML into storage.

Worth noting what I didn't find, because it cost hours. There is also a parameter-source difference: validation reads the POST body while a query-string channelId is accepted without checks. I built an entire campaign around smuggling payloads through the query string. The consumer reads the body. Every one of those payloads delivered the literal string 1. The prefix rule above is the real door, and it is simpler.

Step 06 · The wrong turn

Diagnosing a sanitiser that was never there

The obvious reading of that table is an HTML sanitiser with a tag allowlist that strips on* handlers. I committed to it and spent a long time there:

  • Twelve mutation-XSS vectors. <math><mtext><table><mglyph><style>, <svg><style>, <noembed>, <xmp>, <template>, <iframe srcdoc>, javascript: in <object data>. All silent.
  • CSS exfiltration. Since stylesheets execute, I used @font-face with unicode-range to leak which characters render, and attribute selectors to test attribute contents. This worked: I pulled per-element character sets out of the reviewer's DOM with no JavaScript. It just proved the flag was not on that page.
  • <base href> hijacking. Accepted, and it does retarget relative URLs, but only ones in the injected markup; the page's own resources resolve before our injection point.
The mistake

I diagnosed from a symptom, handlers don't fire, instead of testing the mechanism. A sanitiser removes the tag. A Content-Security-Policy leaves the tag and refuses to run it. My remote <script src> failed because it was cross-origin, not because it was a script, and I never ran the one experiment that separates those two worlds: a same-origin src.

Worth stating plainly: I never read the policy. None of the public endpoints send a Content-Security-Policy header at all, and the reviewer's page lives at http://web/, which is not reachable from outside. The policy is inferred from behaviour.

But the behaviour pins it down. A sanitiser with a tag allowlist would have removed the <script> element; instead the tag survives and simply refuses to run when its src is cross-origin. Point that same tag at the challenge's own origin, as the next step does, and it executes. Handlers dead, remote scripts dead, same-origin scripts alive is the exact signature of script-src 'self' with no 'unsafe-inline'.

Either way the practical conclusion is the same, and it reframes the problem completely. The question is no longer "find a tag the sanitiser missed". It is "find any URL on this origin that will return JavaScript I control", because whatever is enforcing this will trust it unconditionally.

Step 07 · The gadget

An endpoint that hands you executable JavaScript

So I went back to /api/, but looking for something specific. The stock API wordlist finds nothing:

Change the question

Knowing the policy is script-src 'self' changes what you are hunting for. You are no longer looking for any endpoint. You are looking for endpoints that return JavaScript, which is a much shorter list of words, and one you write yourself.

What JSONP is, and why it is dangerous here

JSONP predates CORS. It solved a problem the Same-Origin Policy created: a page could not read JSON from another origin, but it could always load a script from one, because <script src> was never subject to the SOP. So servers wrapped their JSON in a function call and let the caller name the function:

The whole design rests on callback being a function name. This server never checks that. Anything you put in the parameter is pasted straight into a response served as application/javascript, so the endpoint will hand you any JavaScript you ask it for, from the challenge's own origin.

Why this beats the CSP

script-src 'self' means "only run scripts from my own origin". It is an assertion about where a script came from, never about what is in it. A reflective JSONP route turns the origin itself into a source of attacker-controlled JavaScript, so the policy's own definition of trust becomes the way through it. Any endpoint that echoes input into a JS response is a script gadget, and one is enough.

Encoding, two layers

This is where most attempts break. The JavaScript is URL-encoded once so it survives as a query parameter inside src="…", and then the whole payload is form-encoded again for the request body. Encode once and the callback truncates at the first & or =; forget the outer layer and the body parser mangles it.
