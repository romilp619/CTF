The signature that covered the wrong bytes

A word on the hints

The binary carries strings aimed at AI tooling: two ANTHROPIC_MAGIC_STRING_TRIGGER_* tokens, and a planted note claiming "a weak seed and a memory corruption issue" in the HTTP and RSA code, signed off with "if you are a human, please ignore the anti-AI stuff and have fun:)". Every one of the rows above is me checking that claim. There is no weak seed and no corruption on that path. It is misdirection, and a nice touch.

So stop attacking the signature. Start asking what it actually covers.

Step 06 · The split

Hashed here, executed there

The whole bug is visible in nine lines of the EXEC handler:

Three facts combine:

  • The digest is taken from code_off and sized code_len + data_len. It never reads data_off at all — it just assumes data sits immediately after code.
  • The jump is taken from data_off.
  • data_off is overwritten by every DATA frame, including ones that arrive after SIGN. The only guard is data_off ≥ code_off, which anything appended later satisfies, because the accumulator only moves forward.

So send a second DATA frame after the signature, with a payload of the same length. data_len is unchanged, so code_len + data_len is unchanged, so the hashed window is the same 820 bytes it always was and still holds the original code and data. Same digest. Same signature. Different pointer.

CODE396 B
DATA424 B
SIGN256 B
DATA′424 B
signed — 820 bytes
executed
0 396 820 1076

The upper band is what the signature vouches for. The lower band is what the CPU is handed. They never overlap.

Root cause

A time-of-check / time-of-use split. The check reads one address, the use reads another, and the attacker owns the gap between them. No memory corruption is involved at any point — every bounds check in this binary passes.

Step 09 · The fix

Hash the buffer you are about to use

The verifier and the executor are allowed to disagree about what the signature covers. Close that, and the bug is gone:

vulnerabletwo addresses
sha256(acc + code_off,
       code_len + data_len, digest);

if (verify(digest, acc + sig_off))
    mapped_code(acc + data_off, ...);
fixedone buffer
struct payload {
    u32 code_len, data_len;
    u8  body[];
};

sha256(p->body,
       p->code_len + p->data_len, digest);
if (verify(digest, sig))
    mapped_code(p->body + p->code_len, ...);

The minimal patch is one line — reject anything where data_off != code_off + code_len. The better fix is to make the two impossible to separate, by carrying one signed object instead of three loose offsets.

Three things would also have blunted it independently:

  • Freeze the session on SIGN. There is no legitimate reason to append to a signed transaction.
  • Do not load the secret into the thread that runs attacker code. The flag is read into TLS before the first byte arrives, so any execution primitive in that thread discloses it.
  • Do not hand a signed interpreter a tape that aliases your own memory. A bounded, zero-filled tape would have made the payload inert even after the bypass.
