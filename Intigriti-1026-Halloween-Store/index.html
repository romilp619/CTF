Step 02 · The arithmetic

Sixty cents short, on purpose

There are two discount codes. One is printed in the header of every page. The other you get by signing up to the newsletter, which accepts any address at all.

CodeDiscountHow you get it
NIGHT2020%printed in the site-wide announcement bar
NEWS3030%POST /api/newsletter, any address, gated per session

They add up rather than compound, so both together is 50% off. That still leaves €333.00 to pay out of €66.00. To afford the box I need the total down to 6600 or under, which works out at 90.09% off.

And here's the bit that gave the game away. With only 20s and 30s to play with:

Read the numbers

Those prices aren't random. Being 60 cents short means one duplicate coupon isn't enough on its own. Whatever the bug is, it has to work over and over. That told me to stop looking for a secret 90%-off code and start looking for a way to reuse the ones I had.

Step 04 · The tell

A result I could not reproduce

Early on, while firing variants at the endpoint, I caught the cart in this state:

Every clean session rejected the duplicate. Case and whitespace variants did nothing. Racing it did nothing. I genuinely started wondering whether I'd misread my own terminal.

What actually fixed it was giving up on new tests and going back through the request log from the session where it worked. One thing was different there: I'd applied two different codes to that cart. Every attempt to reproduce it had only used one.

The hypothesis

If the duplicate check does not scan the promotions list but inspects only the last entry, then a code is blocked only while it is the most recent one. Apply a different code after it, and it becomes eligible again.

That is falsifiable in one request.

Step 06 · The bypass

Alternate, and it never stops

So alternate them. Neither code is ever the most recent one by the time it comes back round, so every single application gets accepted, and each one adds another slice off the same cart.

1NIGHT2020% off€532.80
2NEWS3050% off€333.00

4NEWS30duplicate ×2100% off€0.00

At zero, canCheckout flips to true and checkout goes through. Nothing stops you carrying on past that either. I stopped at 100% only because the box was already free.

One more thing

The same endpoint also kills the shop

A separate defect, found while fuzzing the coupon field. Sending a non-string code crashes the application outright:

Sessions are held in memory, so every crash wipes every shopper's cart and the next request comes back session_required. One request, repeated, keeps the shop down. I confirmed it once and left it alone after that, mostly because it kept knocking over my own testing.
