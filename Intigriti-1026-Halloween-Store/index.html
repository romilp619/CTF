Step 02 · The arithmetic

Sixty cents short, on purpose

Two promotion codes exist. One is advertised in the header of every page; the other is handed out by the newsletter endpoint to any email address you like.

Worth keeping even though it did not crack this one: with an empty cart, a valid code returns empty_cart and an invalid one returns invalid_coupon. Codes can be enumerated with no cart and no mutation at all — which is how I cleared 1842 candidates and proved there was no hidden 90%-off code to find.

Step 05 · The tell

A result I could not reproduce

Early on, while firing variants at the endpoint, I caught the cart in this state:

Clean sessions rejected duplicates every time. The variant sweep found nothing. The race was serialised. For a while I assumed I had misread my own output.

What broke it open was re-reading that session's request log rather than running more tests. One variable was present there and absent from every reproduction attempt: two different promotions had been applied to the cart. All my duplicate tests had used a single code.

The hypothesis

If the duplicate check does not scan the promotions list but inspects only the last entry, then a code is blocked only while it is the most recent one. Apply a different code after it, and it becomes eligible again.

That is falsifiable in one request.

Step 06 · The rule

Confirmed in three requests

The rule is confirmed: a code is blocked only while it is the last one applied.

Step 07 · The bypass

Alternate, and it never stops

Alternating the two codes means neither is ever on top when it comes back around. Every application is accepted, and each one stacks another percentage onto the same cart.

1NIGHT2020% off€532.80
2NEWS3050% off€333.00
3NIGHT20duplicate ×270% off€199.80
4NEWS30duplicate ×2100% off€0.00

At zero, canCheckout flips to true and the order goes through. There is no upper bound here — the alternation has no termination condition. One hundred percent is simply where I stopped, because the goal was met.
